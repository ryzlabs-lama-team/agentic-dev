## Context

See `proposal.md` for motivation. The existing Claude and OpenCode trees encode the same state machine through runtime-specific agent mechanisms. GitHub currently contains OpenSpec-owned skills and prompt files, so the new toolkit distribution must coexist under `.github/` without treating that whole tree as installer-owned. VS Code supports workspace custom agents, user-selectability, model declarations, tool selection, and an allowlisted worker-agent set; other Copilot clients overlap only partially.

## Goals / Non-Goals

**Goals:**
- Represent the coordinator as the sole user-selectable agent and stage workers as stateless subagents.
- Keep durable handoffs and policy equivalent to the established loop while expressing permissions in Copilot's agent schema.
- Add a narrowly owned, independently manifested installer distribution.
- Make unsupported runtime checks explicit instead of producing false-positive preflight results.

**Non-Goals:**
- Sharing or generating prompts across runtime trees.
- Modifying OpenSpec-generated GitHub skills or prompts, or adding repository-wide instructions.
- Claiming CLI/cloud orchestration parity before an end-to-end topology test.
- Changing Claude or OpenCode semantics, file layouts, or model allocation.

## Decisions

### Use seven `.agent.md` profiles with an explicit flat delegation allowlist

Mirror the OpenCode role split because Copilot model selection is profile-level and an escalation profile makes retry behavior deterministic. The coordinator is user-invocable; workers are not. Only the coordinator receives agent delegation and it allowlists the six worker names. Prompt discipline further confines the coordinator to ledger and status operations.

Alternative: five workers plus a per-spawn model override. Rejected because model override support is not established across target Copilot runtimes and would weaken portability.

### Keep profiles target-neutral but acceptance scoped to VS Code

Omit a restrictive profile target so CLI/cloud can discover profiles where supported. Tests and documentation treat VS Code as the only supported end-to-end runtime and label all others best effort until separately proven.

Alternative: set a VS Code-only target. Rejected because it prevents harmless profile reuse without improving VS Code correctness.

### Retain Luna/Terra/Sol intent through explicit model values

Each profile carries its assigned model configuration. Where supported, an ordered fallback array can include concrete aliases preserving the tier intent. Static checks verify declarations; release acceptance verifies at least one value per profile in the actual VS Code subscription. README records that clients may reject or fall back from unavailable values.

Alternative: omit models and inherit the session default. Rejected because it loses the requested allocation and makes escalation behavior unpredictable.

### Treat GitHub OpenSpec assets as prerequisites, not distribution contents

Only the seven agent profiles and `.github/opsx-loop/` operational files belong to the Copilot installed set. Workers resolve OpenSpec procedures from the existing skill, then prompt, then CLI where possible. The installer enumerates owned paths rather than walking `.github/`.

Alternative: bundle skills/prompts for convenience. Rejected because those files are generated by OpenSpec and may contain repository customizations.

### Expose exactly four installer targets

The installer accepts exactly `claude`, `opencode`, `copilot`, and `all`. `claude`, `opencode`, and `copilot` each select only their named distribution; `all` selects all three and uses the existing classify-all-before-write discipline. The default remains `claude`. The former `both` target is rejected as invalid rather than retained as an alias, making the target contract finite and preventing two names from expressing overlapping multi-runtime behavior.

Compatibility is intentionally breaking only for callers that explicitly pass `both`: they must migrate to `all` when they want all supported distributions, or invoke `claude` and `opencode` separately when they must exclude Copilot. Existing explicit `claude` and `opencode` invocations, the default invocation, installed runtime files, and provenance manifests remain compatible.

Alternative: preserve `both` as Claude plus OpenCode and add `all`. Rejected because the confirmed contract has exactly four targets and retaining an alias would perpetuate an ambiguous legacy union. Alternative: redefine `both` to mean all three distributions. Rejected because it would both violate the exact target contract and unexpectedly write `.github/` files for existing callers.

### Split static preflight from VS Code release acceptance

The shell preflight validates files, declarations, OpenSpec prerequisites, and writable state. If no stable command can inspect VS Code's resolved agents/models, it prints a manual validation requirement. Repository validation checks schema/frontmatter mechanically, while release acceptance uses VS Code to prove actual delegation and model availability.

Alternative: infer runtime readiness from file presence. Rejected because malformed tool names or unavailable subscription models would pass falsely.

## Risks / Trade-offs

- [Copilot agent schema or tool identifiers differ by client version] → Pin documentation to the tested VS Code version and add fixture/schema validation plus a real VS Code acceptance checklist.
- [Configured models are unavailable for a subscription] → Permit documented ordered fallbacks and fail release validation when a profile has no available configured value.
- [Stateless workers miss critical context] → Put complete identifiers, paths, round number, and expected return contract in every delegation prompt; use files as authoritative state.
- [Installer overwrites unrelated GitHub customization] → Explicitly enumerate toolkit-owned paths and test forced and multi-target installs against sentinel skills/prompts/instructions.
- [Automation still passes the removed `both` target] → Reject it with the standard invalid-target path, document the breaking migration, and add a regression test proving no files are classified or written.
- [CLI discovers profiles but cannot delegate equivalently] → Keep profiles target-neutral but documentation experimental until an end-to-end run passes.

## Migration Plan

1. Add and statically validate the Copilot distribution without changing existing trees.
2. Replace the installer target parser and help text with the exact set `claude`, `opencode`, `copilot`, and `all`; preserve the `claude` default and remove `both` without an alias.
3. Update callers and documentation that use `both`: choose `all` when Copilot installation is intended, or separate `claude` and `opencode` invocations when it is not.
4. Run installer regressions for each of the four accepted targets and every conflict mode; verify `all` covers all three distributions, each single target remains isolated, and `both` is rejected before classification or writes.
5. Install into a clean fixture initialized for GitHub Copilot/OpenSpec, run preflight, then execute the VS Code end-to-end acceptance scenario.
6. Publish support/model and breaking-target migration documentation only after primary-environment validation.

Rollback reverts the installer and Copilot distribution as one release unit. Before rollback, users who adopted `copilot` or `all` must remove toolkit-owned Copilot files through the matching supported uninstall/provenance path; rollback must not delete OpenSpec-owned `.github/skills/` or `.github/prompts/`. Existing Claude/OpenCode files and provenance entries remain valid. A rollback to a prior release may restore that release's `both` behavior, but no compatibility alias for `both` is added to this change.
